# Параллельная фиксация нескольких дел

Использовать пакетную очередь, когда нужно получить несколько независимых дел или документов. Единицей параллелизма является целое дело: один worker владеет одним каталогом пакета и одним `capture-state.json`. Никогда не назначать несколько worker’ов на разные страницы одного пакета.

## Разделить ответственность

- **Координатор** проверяет разрешённый способ доступа, оплату, общий объём, запас диска, список дел и лимиты домена; создаёт пакеты и очередь; выполняет итоговый аудит.
- **Worker фиксации** атомарно получает одно задание, работает только в его каталоге, продлевает lease и завершает или освобождает задание.
- **Worker обработки** может собирать кадры, готовить производные и OCR уже законченного независимого дела, не изменяя доказательные кадры.
- Только координатор изменяет общие `research/research-log.md`, `research/strategy.md`, GEDCOM и сводные отчёты. Worker возвращает артефакты и технический результат по своему делу.

Субагенты являются возможной реализацией worker’ов, но не обязательной. Если платформа их не поддерживает, выполнять ту же очередь последовательными процессами. Не зашивать в скилл конкретное число агентов.

## Подготовить отдельные пакеты

Сначала создать и проверить каждый пакет через `init_capture_package.py` и `audit_capture_package.py --preflight`. Затем зарегистрировать относительные пути:

```sh
python3 <путь-к-скиллу>/scripts/init_capture_batch.py batch \
  --job case-001=cases/case-001 \
  --job case-002=cases/case-002 \
  --max-workers 4 --max-per-domain 1

python3 <путь-к-скиллу>/scripts/audit_capture_batch.py \
  --preflight --workers 2 batch
```

Идентификаторы jobs и worker’ов делать техническими и обезличенными. В `batch-state.json` хранятся только относительный путь пакета и домен, а не URL, cookies или архивные сведения. Полные сведения о происхождении остаются в отдельном пакете дела.

По умолчанию одновременно выполнять не более одного задания на домен. `--domain-limit HOST=COUNT` повышать только после проверки условий сайта, фактических ограничений и устойчивости сессии. Общий `--max-workers` не отменяет лимит домена.

После калибровки безопасно изменить лимиты или приоритет, не пересоздавая очередь:

```sh
python3 <путь-к-скиллу>/scripts/configure_capture_batch.py batch \
  --max-workers 3 --domain-limit viewer.example=2 \
  --priority case-002=10
```

Скрипт не позволит опустить лимит ниже уже работающего числа jobs. Повышение лимита не означает разрешения сайта: координатор сначала отдельно подтверждает допустимость.

## Выполнить цикл worker’а

Получить одно допустимое задание:

```sh
python3 <путь-к-скиллу>/scripts/claim_capture_job.py batch \
  --worker-id worker-01 --json
```

Код возврата `0` означает успешный claim, `3` — сейчас нет допустимого задания. Worker использует только возвращённые `job_id` и относительный `package`. Lease предотвращает вечную блокировку после сбоя, но не разрешает доступ и не заменяет соблюдение условий архива.

Координатор может читать состояние без изменения lease:

```sh
python3 <путь-к-скиллу>/scripts/capture_batch_status.py --json batch
```

Во время длинной фиксации продлевать lease заметно раньше половины его срока:

```sh
python3 <путь-к-скиллу>/scripts/update_capture_job.py batch \
  --job case-001 --worker-id worker-01 --heartbeat
```

После получения дела выполнить индивидуальный аудит, записать и строго проверить SHA-256, затем отметить результат:

```sh
python3 <путь-к-скиллу>/scripts/audit_capture_package.py batch/cases/case-001
python3 <путь-к-скиллу>/scripts/write_checksums.py batch/cases/case-001
python3 <путь-к-скиллу>/scripts/verify_checksums.py --strict batch/cases/case-001
python3 <путь-к-скиллу>/scripts/update_capture_job.py batch \
  --job case-001 --worker-id worker-01 --captured
```

При устранимой внешней паузе использовать `--release`, при содержательной или технической ошибке — `--fail 'краткая техническая причина'` без ФИО, URL и чувствительных сведений. Координатор возвращает исправленное задание через `--retry`. Истёкший lease автоматически возвращается в `pending` при следующем claim; новый worker обязан проверить частично сохранённые файлы и продолжить по `capture-state.json`, а не начинать вслепую.

## Учитывать тип доступа

- Публичные официальные файлы и разрешённые IIIF-изображения обычно можно распределять по независимым worker’ам в пределах опубликованных лимитов.
- Для одного авторизованного, платного или ограниченного по времени просмотрщика сохранять лимит один worker на домен и сессию, пока архив явно не допускает больше. Не передавать worker’ам cookies, токены или пароли через prompt, очередь или файлы.
- Не предполагать, что субагент автоматически видит законную браузерную сессию координатора. Если платформа не предоставляет уже авторизованный общий браузер безопасным способом, фиксацию выполняет координатор, а worker получает только сохранённый локальный пакет для обработки.
- Если параллельный доступ к просмотрщику рискован, оставить фиксацию последовательной, а сборку, контрольные суммы, контактные листы и локальный OCR выполнять параллельно по уже закрытым делам.
- Оплату, первичную калибровку сайта и изменение лимитов выполняет координатор; эти действия не делегировать нескольким worker’ам.

## Завершить пакет

После окончания всех jobs повторно проверить пакеты и атомарно перевести успешно проверенные `captured` в `audited`:

```sh
python3 <путь-к-скиллу>/scripts/audit_capture_batch.py \
  --workers 2 --mark-audited batch
```

Полный аудит завершается ошибкой, если осталось `pending`, `running` или `failed`, истёк lease, пакет изменился во время проверки, индивидуальный аудит не прошёл либо `sha256.txt` неполон. Только после этого координатор сводит охват и результаты в общий исследовательский журнал.
