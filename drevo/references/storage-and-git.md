# Хранение доказательств и размер Git

## По умолчанию хранить минимум

Использовать режим `minimal` из `research/evidence/storage-policy.json`, если пользователь явно не попросил об ином.

В Git включать только:

- канонический GEDCOM, журнал, стратегию, конфликты и итоговые отчёты;
- метаданные происхождения, охват, состояние фиксации и индекс холодного хранилища;
- минимальный непрерывный фрагмент источника, который буквально подтверждает или опровергает исследуемое утверждение;
- компактную расшифровку этого фрагмента и контекст, без которого чтение нельзя надёжно проверить.

Не включать в Git сканы, цитаты и расшифровки посторонних записей, людей и частей дела, не связанных напрямую с активным исследовательским вопросом. Для отрицательного результата сохранять диапазон, уровень прохода, варианты поиска и качество изображений, а не массив нерелевантных расшифровок.

## Полные пакеты хранить холодно

- Создавать полную фиксацию вне рабочего Git-дерева или переносить её туда только после технического аудита.
- В холодном пакете хранить все исходные кадры, метаданные и `sha256.txt`. После записи или перемещения заново проверять контрольные суммы.
- В `cold-storage-index.md` хранить логический ID хранилища, относительный путь пакета, число файлов, объём, дату проверки и SHA-256 самого манифеста.
- Абсолютный локальный путь записывать только в игнорируемый `cold-storage.local`, чтобы не публиковать локальные пути.
- Не удалять холодный пакет без другой полной копии с проверенными суммами.

## Проверять staged payload

Перед каждым коммитом запускать:

```sh
python3 <путь-к-скиллу>/scripts/audit_git_payload.py --repository <корень-проекта>
```

В режиме `minimal` скрипт блокирует коммит, если staged-набор превышает лимит одного файла, суммарный лимит или лимит числа доказательных payload-файлов. Лимиты можно сделать строже в `storage-policy.json`, но не ослаблять без осознанного решения.

## Полный режим только по просьбе

Если пользователь явно попросил хранить всё в репозитории:

1. Оценить полный объём, приватность, лимиты хостинга и необходимость Git LFS или другого бэкенда.
2. Изменить `mode` на `full-repository` отдельным видимым изменением.
3. Осознанно изменить шаблонные исключения `.gitignore`; не обходить их случайным `git add -f`.
4. Перед коммитом и перед первым push ещё раз показать пользователю оценку объёма и выбранную схему хранения.
